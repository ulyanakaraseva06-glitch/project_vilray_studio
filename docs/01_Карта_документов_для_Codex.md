# Карта документов для Codex

## Задача этого файла

Этот файл определяет, какие документы читать, когда их использовать и какие документы считать источником истины. Codex не должен пытаться загрузить весь пакет в один контекст и затем импровизировать.

## Порядок чтения перед началом разработки

1. `02_Концепция_продукта.md` — зачем существует сервис и для кого он сделан.
2. `03_Границы_MVP_и_сценарии.md` — что входит в первую версию и что запрещено добавлять.
3. `04_UX_UI_спецификация.md` — компоновка одного экрана, мобильная логика и визуальная связь со «Сравни плитку».
4. `05_Функциональные_требования.md` — все пользовательские функции по модулям.
5. `06_Логика_раскладки_и_расчета.md` — математика, подрезки, количество и запас.
6. `07_Модель_данных.md` — сущности и структура проекта.
7. `08_Техническая_архитектура.md` — стек, папки, сборка и размещение.
8. `09_SEO_GEO_стратегия.md` — индексируемая оболочка и AI-search.
9. `11_Реклама_и_экосистема_проектов.md` — рекламные места и проекты Vilray.
10. `12_Аналитика_и_метрики.md` — события и воронки.
11. `13_Тестирование_и_приемка.md` — критерии готовности.
12. `14_Этапы_разработки_и_архивы.md` — порядок реализации и формат выдачи.

## Правило контекста

Перед изменением отдельного модуля Codex должен перечитать только связанный документ и соответствующие типы/тесты. Не нужно каждый раз перечитывать сводное ТЗ целиком.

## Правило конфликта

При конфликте:

- специализированный документ важнее сводного;
- явное ограничение MVP важнее идеи «сделать лучше»;
- простое решение важнее новой технологии;
- существующая рабочая часть не переписывается без причины;
- новые библиотеки добавляются только после отдельного объяснения.

## Правило отчёта

После каждого этапа Codex обязан сообщить:

- что реализовано;
- какие файлы изменены;
- как запустить и проверить;
- какие тесты пройдены;
- что не сделано;
- какие архивы подготовлены;
- какие решения нужны перед следующим этапом.
